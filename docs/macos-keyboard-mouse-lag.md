# macOS 键盘控制鼠标卡顿排查（2026-09-12–13）

键盘控制鼠标的移动链路需要在后台保持及时响应，并正确处理调度延迟、屏幕边缘和输入中断。以下记录可复现的问题、修复方式及验证边界；尚未完成实际卡顿场景下修复前后的连续对照，不能据此认定某个假设是所有长时间使用卡顿的唯一原因。

## 第一轮现场证据（0.1.2）

- 运行版本 0.1.2；对已运行约 6 小时 49 分钟的进程做了 5 秒采样。采样报告的 physical footprint 为 57.9 MB，峰值为 115.1 MB。没有观察到主线程持续阻塞；单次采样不能排除间歇性阻塞或缓慢泄漏。
- 键盘事件在独立 CGEventTap 线程中进入 MappingEngine。方向变化写入一个共享状态，独立鼠标线程产生约 120 Hz 的移动事件。鼠标移动不经过前端渲染、Tauri 事件队列或 Alt-Tab 工作队列。
- 原来的移动线程即使空闲也每约 8.33 ms 醒来。两个输入线程均未设置交互 QoS，移动过程中也没有 NSProcessInfo 活动声明。
- macOS 的 App Nap 可以降低后台进程优先级和定时器频率，这是合理的嫌疑，但本次没有捕获到该进程处于 App Nap 的直接证据。[Apple：App Nap](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/AppNap.html)
- 另外运行了只观察 Yorling 自带标记鼠标事件的 30 秒采样，该窗口内没有收到移动事件，因此没有可用于比较的真实移动帧间隔数据。

## 第一轮可确认的问题和修复

| 问题 | 原行为 | 修复 |
| --- | --- | --- |
| 调度延迟被换算成大段位移 | 回归测试先在旧实现失败：模拟 2 秒延迟，单帧跳了 2800 像素 | 单帧计算最多使用 16.666 ms；超过 100 ms 的停顿清空速度、重新读取实际位置；不补发错过的帧 |
| 屏幕边缘坐标持续累加 | 系统光标停在边缘，但软件内部位置继续向屏幕外增长，转向时需要先抵消这段距离 | 按真实显示器区域约束并保存内部坐标，支持负坐标和错位排列，活动中每秒刷新显示器列表 |
| 松开后很快重新按下 | 如果两次变化都发生在刷新间隔内，工作线程可能看不到中间的停止，沿用上次的速度和位置 | 用会话计数保留停止和重启的信息，同时仍只保存最新方向，不排队旧移动 |
| 空闲轮询及后台调度 | 无操作仍不断唤醒，输入线程调度意图未声明 | 空闲条件变量等待；按键变化主动唤醒；输入线程使用交互 QoS；移动期间持有活动令牌，空闲和退出自动结束 |
| 监听中断后可能丢失松键 | 仅重新启用 CGEventTap，原移动方向可能残留 | 中断时停止移动并取消鼠标模式，避免继续执行过期的按键状态 |

活动使用 `UserInitiatedAllowingIdleSystemSleep`，不会要求系统或显示器保持唤醒。按 Apple 建议成对调用 begin/end，并在输入互斥锁外执行 Foundation 调用。[Apple：活动管理](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/PrioritizeWorkAtTheAppLevel.html)、[Apple：交互 QoS](https://developer.apple.com/documentation/dispatch/dispatchqos/qosclass-swift.enum/userinteractive)

鼠标线程每帧设有 autorelease pool，及时释放系统框架可能生成的临时对象；这属于资源管理修正，不代表已证明原版本存在这类泄漏。线程启停互斥并 join，防止快速重启重叠工作线程。

## 第一轮验证

- 原实现的延迟回归测试失败，修复后通过。
- `cargo test --workspace`：268 项通过，其中引擎 108 项、macOS 17 项。
- 覆盖持续约 6.94 小时的数学模拟（300 万帧）、10 万次顶住边缘、跨屏/负坐标/屏幕移除、亚像素精度、快速停止再启动、跳过错过的帧、最新方向覆盖、真实工作线程空闲/唤醒/退出、监听中断。
- 数学模拟是快速执行的状态测试，不是让 GUI 在真实系统负载下跑了 7 小时。工作线程测试使用模拟输出，不会移动桌面鼠标。
- `pnpm test`：181 项通过。
- 前端 TypeScript/Vite 生产构建通过；macOS release 应用完成构建，`codesign --verify --deep --strict` 验证通过。启动后的采样确认新鼠标线程在空闲条件变量上等待。

## 重启后的复查与第二轮修复（0.1.3）

重启后再次报告不顺畅。复查发现只有一个 Yorling 主进程，运行路径指向已安装应用；安装版与上一轮构建的可执行文件 SHA-256 一致（`849bdc337ac5…`），签名验证通过。可以排除这次现场“仍在运行旧程序”的解释。复查时应用仅启动约 9 分钟，因此不能直接将这次表现归为长时间运行导致的退化。空闲采样仍显示鼠标线程在条件变量上等待。

显示器模式为约 75 Hz，CoreVideo 返回标称 74.968 Hz；4 秒原生显示时钟采样得到 300 次回调，平均间隔 13.336 ms。上一轮鼠标固定约 120 Hz 更新，没有对齐显示刷新。在匀速、理想显示采样的模型中，1400 单位/秒的移动在 75 Hz 屏幕上会交替显示约 11.67 或 23.33 单位的位移；对齐后约为每帧 18.67 单位。这说明即使没有长时间线程停顿，也存在可解释视觉不均匀的节奏问题，**不证明这就是本次主观卡顿的全部原因**。

第二轮改动：

- 移动时使用光标所在显示器的 CVDisplayLink 节奏，保持独立于 WebView/主线程。回调仅覆盖一个待处理帧并唤醒工作线程，不执行鼠标事件、显示器查询或 Foundation 调用，也不积压帧。[Apple：CVDisplayLink](https://developer.apple.com/documentation/corevideo/cvdisplaylink-k0k)
- 使用显示时间戳计算位移，避免把回调/工作线程的小幅唤醒抖动直接变成速度抖动。跨屏时重新建立时钟并丢弃旧时间戳；负向或无效时间戳退回单调时钟计算。
- 原有单帧位移上限适配正常屏幕周期，避免在 30 Hz 等低刷新屏幕上因固定 16.666 ms 上限而降速。异常间隔仍受限，长停顿不追赶。
- 松键和退出时停止、释放显示时钟。没有可用时钟或超过 100 ms 没有回调时退回定时器；活动期间每秒尝试恢复。CoreVideo 的创建和释放均在输入锁外，保留即时松键唤醒。
- 为兼容项目当前 macOS 部署范围，使用仍可运行的 CVDisplayLink；该 API 已被 Apple 标记废弃。将来提高最低系统版本时可迁移到 NSScreen 的显示时钟；本次不把输入更新绑到 UI 主循环。
- 主应用版本升至 0.1.3，便于区分两轮修复。源码仓库排除本地安装包、压缩包目录、调试输出和签名构建产物；已跟踪的 `app/`、`release/` 文件仅从索引移除，保留本地副本，不重写历史。

另外检查了其他全局输入监听。现场存在输入法的键盘监听，但未发现正在修改鼠标移动事件的第三方监听。系统给出的键盘监听累计延迟包含很大的历史值，不能凭这个统计将卡顿归因于输入法。后续应分别比较持续移动、起步/转向、实体鼠标，以及切换输入法后的表现。

第二轮验证包括 30、59.94、60、75、120、144、240 Hz 速度、显示时间戳抖动与不连续、最新帧覆盖、停止后的帧丢弃、原有边界/长延迟/生命周期回归。另在登录桌面的真实显示时钟上运行了可显式启用的测试：

```sh
cargo test -p yorling-platform-macos native_display_clock_paces_output_and_releases_across_restarts -- --ignored --nocapture
```

同一工作线程使用模拟鼠标输出，测得定时器基线中位间隔 8.329 ms，显示时钟 13.345 ms，重启后的显示时钟 13.341 ms；两次显示时钟的 p95 约 14.3 ms。验证了空闲后没有输出、停止后回调持有的共享状态已释放。**这里的真实部分是显示时钟和工作线程，输出是模拟的，不会移动桌面鼠标，也没有测量肉眼可见的显示帧。**

本轮完整检查：`cargo test --workspace` 273 项通过（另 1 项需要桌面环境的测试已单独运行通过），`pnpm test` 181 项通过，TypeScript/Vite 生产构建与 macOS release 打包通过。0.1.3 已用与原安装一致的开发签名身份签名，`codesign --verify --deep --strict` 通过，并替换、启动安装版；旧版备份已校验。安装后运行路径、版本和可执行文件 SHA-256 均与新构建一致。

## 手动验证与后续诊断

重点观察隐藏主窗口后的持续移动、顶住屏幕边缘再转向、快速松按，以及长时间使用后的手感。测试前确认应用版本为 0.1.3，避免旧进程仍在运行。第二轮复查的 60 秒被动采样没有捕捉到鼠标移动，没有实际掉帧场景的事件对照，因此仍需实际使用验证，不能宣称所有卡顿已经消失。

运行被动诊断工具，并分别连续使用键盘、触控板/实体鼠标移动：

```sh
bash scripts/diagnose-mouse-macos.sh 30
```

工具只统计鼠标移动事件的创建间隔、到达间隔和到达时事件年龄；不记录按键、文本、鼠标坐标或剪贴板内容。结果写入已忽略的 `target/diagnostics/`，单组统计最多保留 30000 个样本。`other_mouse_sources` 可能包括其他软件，不能绝对等同于物理鼠标。超过 100 ms 的间隔单独计数，既可能是停顿，也可能是用户没在移动；短暂松键也会影响分位数。

| 观察结果 | 下一步判断 |
| --- | --- |
| Yorling 事件创建间隔本身不均匀 | 检查显示时钟回调、鼠标线程调度和每帧系统调用耗时 |
| 创建间隔均匀，到达间隔/事件年龄明显波动 | 检查系统事件分发和其他全局输入工具 |
| 两者都均匀，但视觉仍不顺畅 | 检查显示刷新、WindowServer 负载与显示输出；事件采样不能证明显示没有掉帧 |
| 主要是刚按下、松开或转向迟钝 | 对照输入法、按键监听和速度缓动；与持续移动掉帧分开诊断 |
| 没有事件或样本太少 | 本次采样不能形成结论，实际操作时重新采集 |

需要时先正常退出应用，再从仓库根目录启动构建版本并启用日志：

```sh
RUST_LOG=yorling_platform_macos=debug ./target/release/bundle/macos/Yorling.app/Contents/MacOS/yorling 2> yorling-input.log
```

`Mouse frame clock` 显示当前屏幕和刷新率；`Mouse display clock paused/unavailable` 表示使用了定时器退路；`Mouse motion scheduling gap` 表示活动期间出现超过 100 ms 的工作间隔（最多每 10 秒一条）；`CGEventTap interrupted`（旧版为 `CGEventTap disabled`）表示键盘监听被系统暂停。这些日志不包含按键内容。不要仅凭没有日志就排除较短的掉帧，也不要直接归因于内存泄漏。

0.1.4 对截图快捷键、输入事件顺序和中断恢复的后续排查见[键盘快捷键记录](macos-keyboard-shortcuts.md)。
